Interpretation
  Shows: on the test cluster, 10 of the 11 indexes declared for these four collections do not
  exist, including every unique index (requestHistory x2, requests.reference, users.email).
  requestHistory, requests and users hold documents, so those indexes are missing from
  populated collections, not merely not yet created on empty ones. sessions holds no documents
  but does exist, and carries the one declared index that is present.

  Together with the server's own privilege report for this credential
  (docs/evidence/DB-01_layer3_verification.txt, PR #85: "Granted on requestHistory: find,
  insert", "Granted on sessions: find, insert, remove, update", "Database-wide grants: none")
  and the listIndexes refusal (listIndexes_refused_civicconnect-app.txt):
  - on requestHistory and sessions, the server reports the credential's actions and they
    include no createIndex. Observed.
  - no database-wide grant exists that could add one. Observed.
  - on requests and users, that report printed no per-collection action list, so createIndex
    there is shown only indirectly: no database-wide grant, listIndexes refused, and the
    indexes absent. Not directly observed.

  The one index that does exist, sessions.lastSeenAt_1, cannot have been built by that
  credential, which has no createIndex on sessions. Some other user created it. Who, when and
  with what expireAfterSeconds is not recorded (asked of R. van der Merwe, 2026-10-12); the M3 API Test Specification S5 assumed indexes "created
  by hand". The exception confirms indexes are created outside the application.

  Does NOT show: anything about staging (which does not exist yet) or production; the six
  collections not checked; the exact expireAfterSeconds value (pending confirmation above).
