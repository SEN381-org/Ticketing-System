Purpose
Show, in CI, that three gates which used to pass silently without checking anything now
fail or warn. The gaps were found by R. van der Merwe reviewing #91 and fixed in #95.

Method
The demo workflow (.github/workflows/gate02-demo.yml, on the demo branch only) runs the
OLD and NEW gate code side by side. It does not copy the code: it takes the layer step's
`run` block out of each version of ci.yml and the extraction script out of each commit,
and prints their SHA-256 (screenshot GATE-02_2). Each sabotage exists only inside the job
and is undone before the step ends; nothing broken was committed. Each step asserts the
expected outcome, so the job is green only if every assertion held. The NEW script's
SHA-256 in the log (b445a6ea…) is that of scripts/ci/extract-office-documents.sh as
committed on #95, so the run tested the final version, including the trap.

OLD passes silently in cases A1, A2 and B and gives no warning in case C.
NEW fails in A1, A2 and B, warns on each non-zip Office file in C, and produces the same
manifest as OLD. The NEW layer check passes on the intact tree.

What this does not show
- Anything about the real CI jobs failing on a pull request. The gates were run inside
  a demonstration job, not by breaking a branch. Removing src/middleware for real would
  fail the test suite before the layer step runs, which would hide the layer step.
- That the layer check catches every bypass. It still does not catch require or
  createRequire, or a cross-module collection read (PED M3.5.4).
- That a non-zip Office file is scanned usefully. It is scanned as raw bytes, which
  cannot read text inside an encrypted workbook. The new behaviour is a warning, not a
  failure, so the two lock files will warn on every run until they are removed from
  history.
